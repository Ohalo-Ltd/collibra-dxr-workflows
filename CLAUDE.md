# collibra-dxr-workflows

The **Data X-Ray ↔ Collibra integration**: six Collibra workflows (Groovy + BPMN + JSON forms) released together as **two bundles** — the `onprem` edition (scripts call Data X-Ray directly) and the `cloud-edge` edition (Collibra Cloud reaches Data X-Ray through an Edge site's HTTP connection). This is a *workflow pack* built and deployed with the [collibra-workflower](https://github.com/Ohalo-Ltd/collibra-workflower) harness — see that repo's CLAUDE.md for packaging format, config-variable rules, redeploy semantics, REST testing tips and the Groovy runtime facts. This file holds only what is specific to the Data X-Ray workflows.

## Layout

```
pack.json                  Pack manifest: bundle name, pinned harnessRef, workflow list, extra bundle files,
                           variants {onprem, edge} → one bundle each
shared/*.groovy            Function-only Groovy included into scripts at build time (`// {{include:x.groovy}}`);
                           the ONLY place that knows the Data X-Ray API (dxr_search / dxr_catalog_sync / dxr_rows;
                           dxr_http_direct = the on-prem transport)
workflows/<name>/          One directory per workflow (app.json, BPMN template(s), scripts/, forms/); scripts are
                           shared by both editions
  workflow.edge.bpmn.template  SOURCE BPMN of the 4 Data X-Ray-calling workflows (both editions)
  workflow.bpmn.template       on-prem BPMN, GENERATED from the Edge one by tools/derive_onprem_bpmn.py — never edit
  scripts/dxr_call_direct.groovy  the on-prem transport task (only the generated on-prem BPMN references it)
tools/derive_onprem_bpmn.py  Regenerates the on-prem templates; `--check` exits 1 when one is stale
docs/deployment-guide.md   Customer-facing UI deployment guide, on-prem edition (shipped in both bundles)
docs/deployment-guide-edge.md  Customer-facing guide for the Collibra Cloud + Edge edition (shipped in both)
docs/file-asset-lifecycle.md  Customer-facing explainer: file identity, creation, limits, sync, orphaning/retirement, deletion (shipped)
docs/images/               Screenshots referenced by the docs (bundle.extra ships the docs dir, so relative links survive)
docs/acceptance-criteria.md  Lifecycle acceptance criteria / UAT checklist (shipped in the bundle)
docs/standalone-classification-sync.md  How to run tools/sync_classifications_standalone.py (Python twin of the classification sync, shipped)
tools/sync_classifications_standalone.py  Standalone REST re-implementation of the classification sync — keep its CANONICAL IDS block in step with configure_data_xray.groovy
workflow-registry.json     Workflow name → Collibra definition UUID, per environment (dev instances)
.github/workflows/release-bundle.yml  Builds the release bundle with the pinned harness on `release: published`
```

Developing: work from a checkout of the harness with this repo mounted at `packs/dxr-workflows` (`git clone --recurse-submodules`). From the harness root: `python deploy.py search-data-xray --dry-run` (default variant `onprem`), `python deploy.py search-data-xray --variant edge`, `python deploy.py bundle --pack packs/dxr-workflows` (both bundles), `python tools/groovy_syntax_check.py packs/dxr-workflows` (compiles every script of every variant with `groovyc` — run it after touching `shared/`). Commit and push pack changes *inside* `packs/dxr-workflows`, then bump the submodule pointer in the harness.

Releasing: `gh release create vX.Y.Z --generate-notes` in this repo. CI checks out the harness at `pack.json`'s `harnessRef` and attaches `collibra-data-xray-workflows-onprem-vX.Y.Z.zip` **and** `collibra-data-xray-workflows-cloud-edge-vX.Y.Z.zip`. If a harness change alters the ZIP output, bump `harnessRef` first (variants + includes need harness ≥ v2.2.0).

## Two editions, one code base (since v3.0.0)

Both editions run the same scripts against the same Data X-Ray API (`POST /api/indexed-files/search` plus the internal catalogue endpoints). Every Data X-Ray call is one turn of a loop: a script **arms** the request (`armDxrRequest`) → an async **transport task** runs it → the next script **reads** the response (`readDxrResponse`). Only the transport task and the configuration variables differ, which is why the on-prem BPMN can be generated:

| | `onprem` (default variant) | `edge` variant → `cloud-edge` bundle |
|---|---|---|
| Transport task | async script task `dxr_call_direct.groovy` → `performArmedRequestDirect()` (`shared/dxr_http_direct.groovy`): HTTPS to the base URL with the Bearer token, writes the same response variables and never throws | Collibra **External API task** bound to an Edge HTTP connection; scripts never open HTTP; **100 KB response cap** |
| Config variables | `dataxrayUrl`, `dataxrayAuthToken` (sentinel defaults, required), `dataxrayPageSize` (default **100**) | `dataxrayConnectionName` (default `data-xray`), `dataxrayPageSize` (default **25**), `dataxrayUrl` (links only, optional) |
| Edition detection | `dxrEdition()` (`dxr_config.groovy`): `edge` iff the process declares `dataxrayConnectionName`; `checkDxrTransport()` validates the right variables and says what to fix | |

**Switching editions loses the variables the other edition does not declare** (Collibra drops undeclared formProperty values) — re-enter the Bearer token when going back to on-prem. Everything else — paging, shrink/skip, the results file, import, rerun, retire, classification sync, criteria rebuild — is shared: `shared/dxr_search.groovy`, `dxr_catalog_sync.groovy`, `file_batch.groovy`, `classification_sync.groovy`, `rerun_common.groovy`, `search_common.groovy`, `collibra_lookup.groovy`. `configure-data-xray-workflows` and `sync-data-xray-files-nightly` have a single BPMN. Shared files hold only `def` functions and use fully-qualified DTO names (imports must stay at the top of the glue script). The harness includes each file once per script, so diamond includes are fine. Everything after the first task is async in both editions: a failure ends in a *Search Failed* / *Sync Failed* user task (`searchFailed`/`syncFailed`), a rerun sets `rerunAborted`; only the synchronous prepare/collector scripts can throw into the start dialog.

**Before v3.0.0** the on-prem edition streamed `GET /api/v1/files?q=<KQL>` (NDJSON, whole result set) into a gzip+Base64 work list and keyed file assets on the Data X-Ray file id. It was dropped because `/api/v1/files` carries no `object_id` and cannot be paged.

## Data X-Ray access and Edge facts (verified on ohalo.collibra.com, Collibra Cloud 2026.09 + Edge 2026.6, Sept 2026)

**External API task** (`<serviceTask flowable:type="http">` + `<design:http-connection-name>${dataxrayConnectionName}</…>`): method/path/headers/body are expressions (`dxrMethod`, `dxrRequestPath`, `dxrRequestHeaders`, `dxrRequestBody`, armed by `armDxrRequest`); the relative path is appended to the connection's Host; response body → `dxrResponseBody` (String), `dxrResponseStatusCode` (Integer), `dxrResponseReason`, `dxrResponseHeaders`. Every status is "success" (a 404 is just status 404). Response cap: **100 KB** (confirmed by Collibra support for TRC's instance, Sept 2026; ohalo.collibra.com happened to allow ~512 KB — do not rely on that). An oversized body sets `dxrErrorMessage` = *Response size exceeds the allowed limit.* and, with `ignoreException=true`, the flow **continues** with no body — `readDxrResponse()` turns that into a retry/abort/fallback. ~0.5–2 s per call. **A non-existent connection name is a pre-validation failure: the instance goes into error (dead-letter job), no task, nothing a script can catch** — documented in the Edge guide's troubleshooting table. `execution.removeVariable` works; `readDxrResponse()` clears the response variables so a retry can never read a stale body.

**Why the internal search API** (both editions): `/api/v1/files?q=` exports the whole index and filters the KQL in memory (`FilesV1Resource` + `KqlResponseFilter`), so it cannot be paged, and its rows carry no `object_id` (`FileServiceImpl.FileMetadataMapper`). The on-prem Bearer token is accepted on every `/api/**` path (one `JWTFilter`, `SecurityConfiguration`; verified on demo 2026-09-29). `POST /api/indexed-files/search` pages with `pageNumber/pageSize`, keeps a consistent snapshot with `usePIT`/`pitId`, returns an exact `hits.total.value` and `max_result_window` (10,000 default; 30,000 on demo), and accepts `excludedFields` with wildcards. Sort `[datasource_id asc, ds#file_name.raw asc]` (what DXR's own export uses) makes from/size paging stable. Ceiling: a query with more hits than `max_result_window` can be previewed but not imported — moot since imports are capped at `dxrMaxImportFiles()` = 10,000.

**Row → tuple mapping** (`tupleFromSearchHit`): `_id` → fileId (Data X-Ray ID attribute only); `datasource_id` + `object_id` → **identity** (tuple [8], [9]; a hit without them is dropped); `ds#file_name`, first `ds#parent_folder_paths` + `/` + name → path; `ds#file_size`; `metadata#MODIFIED_DATE`; `datasource_id` → name via `/api/datasources/browse`. Classification refs: labels = `dxr#tags` (numeric tag ids → uuid via `/api/tags`), annotators = `annotation_stats#unique_phrase_count.<numericId>` > 0 (→ uuid via `/api/data-classes`, six lists incl. read-only ones), extractors = `extracted_metadata#<numericId>` non-empty (→ uuid via `/api/metadata-extractors`). Those UUIDs are what `/api/v1/classifications` returns and what Collibra stores in the Data X-Ray ID attribute, so the existing byDxrId/byName index resolves them. Search and rerun make **no catalogue calls**: the classification sync (both editions) stamps each asset's numeric index id in the **Data X-Ray Index ID** attribute (`dataxrayIndexIdAttrTypeId`, created by configure), and `buildSearchClassificationIndex()` derives every mapping from Collibra. Datasource names are fetched per id (`GET /api/datasources/<id>`, header `api-version: V3`) the first time a page mentions the id and cached in `dxrDatasourceNames`. **Classification sync (`shared/dxr_catalog_sync.groovy`)**: `/api/v1/classifications` is one body (~340 B/item, ~300 KB at TRC) so it is never used through Edge; the sync loads `/api/tags`, `/api/metadata-extractors` and the complete `/api/data-classes`, and when Collibra refuses the last one as oversized it falls back to `/api/datasources/ingester/index/classes` (annotators **with findings** only — NOT the catalogue; trusting it as complete retired 45 dev assets on 2026-09-16) plus `/api/data-classes/<id>` per unknown annotator, and in that mode never retires annotators (`noRetireTypeIds`). The sync must run before the first search, in both editions (`unresolvedCriteriaMessage`).

**Criteria → `query_items`** (`composeQueryItems`; each criterion its own AND group, `group_id` increments): label `{parameter:"dxr#tags", value:"<tagId>", type:"number", match_strategy:"exact"}`; annotator `{parameter:"annotators", value:"annotation.<id>", type:"text", match_strategy:"exists"}`; extractor `{parameter:"extracted_metadata#<id>", type:"text", match_strategy:"isSet"}` (`exists` → HTTP 400); phrase `{parameter:"annotation.<id>", value:"<text>", type:"text", match_strategy:"contains"}` repeated per picked annotator inside one group (first `AND`, rest `OR`; no annotators picked ⇒ every annotator in the catalogue). A criterion whose UUID the catalogue lacks → unresolved → clean failure, never a broadened query. **Gotcha:** the catalogue is what the *connection's* Data X-Ray user can see — a label synced by a user in another organisational unit is "not visible through this connection".

**Page sizing** (matters for Edge; on-prem pages of 100 are ~125 KB and fine): `defaultExcludedFields()` drops phrases, raw text, computed/entitlement fields → 25 rows ≈ 30–40 KB under the 100 KB cap. `dataxrayPageSize` defaults to 25 (BPMN default too — it was 50 until Sept 2026) and is clamped to 1–100 (`dxrDefaultPageSize`/`dxrMaxPageSize`); the search preview, import and rerun all use it. Rows are much larger on some instances (TRC, Sept 2026: 50 rows > 100 KB), so an oversized page is **not** retried as-is: `shrinkFilesPage` re-arms the same rows with the largest size ≤ half that divides the row offset (DXR pages from `pageNumber × pageSize`), keeps it for the rest of the run (`dxrPageSizeCur`; offset is always `dxrPageNo × dxrPageSizeCur`), and once one row alone is too large, re-asks for that row with `identityOnlyExcludedFields()` (everything but `datasource_id` + `object_id`, a few hundred bytes), skips it (`skipResultRow`, `opts.onSkip(assetId)`: counted as failed; the rerun adds that asset id to the seen set, or sets `rerunRetireUnsafe` if the identity could not be read) and grows back towards the largest size that worked (`dxrPageSizeOk`, `dxrRegrowTo`). `onPageZero` runs on the first page that *arrives* (`dxrFirstPageDone`), which is not page 0 when row 0 was skipped. The import starts at the size the preview ended on. Rerun chunks (`rerunSeenChunk_<n>`) count processed pages, not `dxrPageNo`, which is renumbered on a shrink.

**Results file (search, both editions)**: after the preview, `search_page.groovy` runs a second pass (`dxrSearchPhase` = `file`) with `beginFilesPass(resultsFileExcludedFields())` — only `datasource_id`, `object_id`, `ds#file_name`, `ds#parent_folder_paths` survive (~300 B/row, demo) — at 100 rows/request on the preview's PIT, storing CSV text chunks `resultsFileChunk_<n>`; `search_finalize.groovy` zips them into the on-prem `results.csv` (`Datasource,Path`) and attaches it. `resultsFileStatus`: `none` (0 hits) | `complete` | `tooMany` (> min(`dxrMaxImportFiles`, `max_result_window`)) | `failed` (the search still succeeds). **Every pass calls `beginFilesPass()` first** — it resets the pass state and the field exclusions; without it an import after the file pass would request slim rows and lose all classification evidence. The import starts at `dxrPreviewPageSize`, not `dxrPageSizeCur`.

**Testing the on-prem edition on dev**: ohalo.collibra.com runs the Edge edition; deploying the on-prem variant over it drops only `dataxrayConnectionName` (its default `data-xray` comes back on the next Edge deploy); `dataxrayPageSize` and `dataxrayUrl` are declared in both editions and keep their stored values (verified 2026-09-29: a stored 50 survived Edge → on-prem → Edge). Instead of setting the Bearer token on the settings page, pass `formProperties: {dataxrayUrl, dataxrayAuthToken}` (harness `.env` `DXR_BASE_URL`, `DXR_API_KEY`) on `POST /rest/2.0/workflowInstances` — start-time overrides of `readable="false"` properties work (harness CLAUDE.md). Redeploy `--variant edge` afterwards.

**Testing recipe (Edge)**: deploy with `--variant edge`; on ohalo.collibra.com the Edge site `ohalo-edge-integration` has two HTTP connections: **`data-xray`** (Basic auth, a dedicated DXR service account in the same organisational unit as the on-prem Bearer token's user — use this one; credentials live only in the harness `.env`) and the older **`ohalo`** (user `life_sciences` @ demo.dataxray.io — org unit 8, so its labels differ; read-only annotators such as *Email (Regex)* are visible to both). ## Access control for the Data X-Ray workflows

Two custom **global roles** gate the Data X-Ray workflows. Both are created (idempotently, with fixed canonical UUIDs) by `configure-data-xray-workflows`:

| Role | UUID | Purpose |
|---|---|---|
| `Data X-Ray Admin` | `019e9000-abcd-7000-a115-74a17d050000` | Granted the `WORKFLOW_ADMINISTRATION` global permission so holders (alongside Sysadmins) can edit each workflow's Base URL + Bearer token. ⚠️ That permission is **global** — it confers admin over *all* workflows on the instance; Collibra has no per-workflow admin permission. |
| `Data X-Ray User` | `019e9000-abce-7000-9e7d-a7a7115e0000` | Bare membership role, no permissions. Only gates who may *run* the search/sync workflows. |

**No delete-enforcement role**: a "Classification Manager" resource role (mirroring Admin membership onto the Classifications domain via responsibilities) was built, verified and then **deliberately rolled back** (Aug 2026) — Collibra's default already denies asset deletion to anyone without an explicitly granted delete-capable responsibility, so the extra role added moving parts without adding real protection. The guidance is documentation-level: don't grant Steward/Owner-style responsibilities on the Classifications/Files domains. (Learned along the way, kept for reference: `responsibilityApi` IS injected into workflow scripts even though `stubs/CollibraStubs.groovy` doesn't list it; resource permissions on a *global* role would apply instance-wide, so scoped grants require a resource role + responsibility.)

**Who can run** = the workflow definition's start roles, set *only* at runtime by `configure-data-xray-workflows` (Phase 7) via `workflowDefinitionApi.changeWorkflowDefinition(...)` with `startRoleIds`. This is a **partial PATCH** — only `startRoleIds` is sent, so configuration variables (the admin-set token/URL) are **not** wiped. search/sync/rerun → User + Admin; the two nightlies + configure → Admin.

⚠️ **The BPMN's `flowable:candidateStarterGroups` is inert in Collibra** — verified by test: a fresh deploy lands with *no* start-role restriction (`startRoles` empty) regardless of what the attribute says, and configure's BPMN says `flowableUser` yet its enforced `startRoles` is `[Data X-Ray Admin]`. Leave it at the canonical `flowableUser` (matches real Workflow Designer exports); do **not** try to encode access there. The read model exposes start roles as `startRoles` (array of role objects); the *request* field is `startRoleIds` (UUIDs) — don't confuse the two when inspecting via REST.

**Start roles persist exactly like configuration variables.** An in-place redeploy/re-import (POST upsert, same definition UUID) **preserves** `startRoles` — verified. They reset to unrestricted only if a workflow is **deleted** and reimported (same rule as config vars). So after a delete+reimport, **re-run configure** to re-assert access.

**Configuration variables are not per-role.** `readable="false"` already hides the Base URL + token from *everyone* who starts a workflow (any role); only Sysadmin / `WORKFLOW_ADMINISTRATION` holders can edit them on the settings page. Granting `Data X-Ray Admin` that permission is the only lever — nothing "hides" the token from Users because it already is hidden.

**Bootstrap (2 steps).** Import/deploy all six workflows, then run `configure-data-xray-workflows` once (as a Collibra admin / Sysadmin) — it creates the roles and stamps `startRoles` on every deployed target in a single pass. configure skips run-access for any workflow not yet deployed, so if you run it before everything is imported, **re-run it** once the rest are in.

## File import model (gated import + rerun + nightly sync)

Search results can be imported as **Data X-Ray File** assets in the **Data X-Ray Files** domain (canonical UUIDs in `configure_data_xray.groovy`, hardcoded as constants in the scripts). Key mechanics:

- **Upsert key** (v3.0.0): deterministic asset UUID = `UUID.nameUUIDFromBytes("dxr-file:<datasource_id>:<object_id>")` (`fileAssetIdOf(tuple)`, `dxr_rows.groovy`) — the pair Data X-Ray itself dedupes on (`ElasticsearchClientIngester` term query on `datasource_id` + `object_id.keyword`), so it survives rescans and index rebuilds, which reassign the random ES `_id` (the pre-3.0 key). `object_id` is the path on SMB/NFS/S3/Azure/GCS/SFTP/SharePoint on-prem (rename/move → new asset) and the source item id on SharePoint Online (`<library>/<listId>/<driveItemId>`), OneDrive, Google Drive, Gmail, Box; a recreated datasource gets a new `datasource_id`. No lookup index needed — `assetApi.exists(id)` is the upsert check, and any query's import/rerun converges on the same asset per file.
- **Names**: full name = filename + ` [8-hex-of-UUID]` suffix (per-domain name uniqueness vs duplicate filenames at 10k scale); clean filename in `displayName` (the File type has `displayNameEnabled`).
- **Per-query membership**: dedicated **returns/returned by** relation type (query → file). Do NOT use `groups` (7017) for this — 7017 already means query→classification and file→classification.
- **Retire, never delete**: rerun unlinks files no longer returned, then retires (status Obsolete `…005011`) only files **no** query returns any more; reactivates (Candidate `…005008`) on reappearance. The classification sync uses the same retire semantics for orphaned classifications. A run that returns **0 results skips retirement** (transient-outage guard).
- **Batch loop**: each transport task fetches one page and the following async script upserts it as one batch (`handleFilesPage` → `importFilesPage` → `processFileBatch`, `shared/file_batch.groovy`), looped by an exclusive gateway on `${hasMoreWork}`; one page = one transaction.
- **Instance-wide cap**: max **25,000** assets total in the Files domain (projected = current population + net-new); a search above **10,000** hits (`dxrMaxImportFiles`) cannot be imported at all (user asked to refine; reruns unaffected), warning above 5,000. Enforced in the scripts (forms are bypassable), surfaced via form visibility bindings.
- **Keep-in-sync**: tag `dataxray-keep-in-sync` on the query asset; `sync-data-xray-files-nightly` (02:30, after the 02:00 classification sync) starts one **headless** `rerunDataXraySearch` per flagged query via `startWorkflowInstances(... formProperties([headless: 'true']))`. Headless runs never throw and skip the summary user task via a gateway on `${headless == 'true'}`. Flagged queries whose status is **Obsolete are skipped** — archiving a query pauses its nightly sync (manual rerun still allowed); reactivating resumes it. The driver then runs an **orphan sweep**: any Files-domain asset with no "returns" relation from any query is retired — this is what cleans up after a *deleted* query asset (Collibra deletes its relations with it, and per-query retire passes can never see it). The sweep aborts on any scan failure rather than retiring from a partial picture. Timer-start workflows can also be started manually via `POST /workflowInstances` (verified) — handy for testing.
- **Relation reconciliation**: the batch stage diffs each pre-existing file's `groups` links against the row's current hit evidence — stale links (label deleted/unassigned in DXR) are REMOVED, not just skipped. A result row carries the file's complete classification state, so this is query-independent.
- **Rerun exclusivity/scoping**: `rerunDataXraySearch` runs with exclusivity `UNCONSTRAINED` (default RESOURCE_EXCLUSIVITY hides the start action while a summary task is open and would block the nightly fan-out). It cannot be scoped to the query asset type — asset-type assignment rules reject workflows with **global** start roles (`workflowWrongRoles`) — so `rerun_collector.groovy` hard-guards the item's asset type at runtime.
- **Rerun criteria**: rebuilt from the query asset's 7017 relations (classifications' **current** names — DXR renames just work) + the "Annotated Text Filter" attribute, scoped to the annotators linked by the query's **searches text in / text searched by** relations (`019e9210-f2a1-…`, created by configure). Composition (`composeQueryItems`): every label/extractor/annotator is its own AND group; the phrase is one group OR-ed across the annotators explicitly picked for the text (agreed with Colin Walker, Aug 2026). The KQL form (`dxr_query.groovy`) is only the human-readable "Data X-Ray Query" attribute. A criterion whose asset is Obsolete (deleted in DXR) fails the rerun with a message naming it — never silently broadens the query. The "Data X-Ray Query" attribute is a human-readable record of the last run, not rerun input.
- **DXR row-shape assumptions** live in one shared function, `tupleFromSearchHit` (`shared/dxr_search.groovy`); the tuple layout is documented in `dxr_rows.groovy`. Verify against a live response when DXR versions change. Hit-evidence rule: a classification listed as *checked with 0 hits* must NOT get a relation (`annotation_stats#unique_phrase_count.<id>` > 0).


## Data X-Ray API facts (verified against a Data X-Ray demo instance)

- Internal search hit `_source` families (demo, 2026-09): `datasource_id` (int), `object_id`, `ds#file_name`, `ds#parent_folder_paths` (list, ≤ 1 item), `ds#file_size`, `metadata#*`, `dxr#*` (incl. `dxr#tags`, `dxr#raw_text`), `annotation_stats#*`, `extracted_metadata#*`, `computed.*`. `excludedFields` is passed straight to Elasticsearch `_source.exclude` (`SearchRequestProcessor.addExcludedFields`), so wildcards work; there is no include list.
- **No UI link field** on file rows — don't fabricate deep links.
- `object_id` per connector, sampled on demo 2026-09-29: SMB and Folder Path = the path (== `ds#parent_folder_paths[0]` + `ds#file_name`); SharePoint Online (Graph) = `<library>/<listId uuid>/<driveItem id>`.
