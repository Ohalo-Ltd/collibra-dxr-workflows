# collibra-dxr-workflows

The **DataXray ↔ Collibra integration**: six Collibra workflows (Groovy + BPMN + JSON forms) released together as **two bundles** — the `onprem` edition (scripts call DataXray directly) and the `cloud-edge` edition (Collibra Cloud reaches DataXray through an Edge site's HTTP connection). This is a *workflow pack* built and deployed with the [collibra-workflower](https://github.com/Ohalo-Ltd/collibra-workflower) harness — see that repo's CLAUDE.md for packaging format, config-variable rules, redeploy semantics, REST testing tips and the Groovy runtime facts. This file holds only what is specific to the DataXray workflows.

## Layout

```
pack.json                  Pack manifest: bundle name, pinned harnessRef, workflow list, extra bundle files,
                           variants {onprem, edge} → one bundle each
shared/*.groovy            Function-only Groovy included into scripts at build time (`// {{include:x.groovy}}`);
                           the ONLY place that knows the DataXray API (dxr_rows / dxr_http_direct / dxr_edge)
workflows/<name>/          One directory per workflow (app.json, workflow.bpmn, scripts/, forms/)
  workflow.edge.bpmn.template  Edge-edition BPMN template (4 DXR-calling workflows only); scripts/edge/*.groovy its glue
docs/deployment-guide.md   Customer-facing UI deployment guide, on-prem edition (shipped in both bundles)
docs/deployment-guide-edge.md  Customer-facing guide for the Collibra Cloud + Edge edition (shipped in both)
docs/file-asset-lifecycle.md  Customer-facing explainer: file asset creation, 25k cap, sync, orphaning (Not in any search), deletion (shipped)
docs/images/               Screenshots referenced by the docs (bundle.extra ships the docs dir, so relative links survive)
docs/acceptance-criteria.md  Lifecycle acceptance criteria / UAT checklist (shipped in the bundle)
docs/standalone-classification-sync.md  How to run tools/sync_classifications_standalone.py (Python twin of the classification sync, shipped)
tools/sync_classifications_standalone.py  Standalone REST re-implementation of shared/classification_sync.groovy — keep its CANONICAL IDS block in step with configure_data_xray.groovy
workflow-registry.json     Workflow name → Collibra definition UUID, per environment (dev instances)
.github/workflows/release-bundle.yml  Builds the release bundle with the pinned harness on `release: published`
```

Developing: work from a checkout of the harness with this repo mounted at `packs/dxr-workflows` (`git clone --recurse-submodules`). From the harness root: `python deploy.py search-data-xray --dry-run` (default variant `onprem`), `python deploy.py search-data-xray --variant edge`, `python deploy.py bundle --pack packs/dxr-workflows` (both bundles), `python tools/groovy_syntax_check.py packs/dxr-workflows` (compiles every script of every variant with `groovyc` — run it after touching `shared/`). Commit and push pack changes *inside* `packs/dxr-workflows`, then bump the submodule pointer in the harness.

Releasing: `gh release create vX.Y.Z --generate-notes` in this repo. CI checks out the harness at `pack.json`'s `harnessRef` and attaches `collibra-data-xray-workflows-onprem-vX.Y.Z.zip` **and** `collibra-data-xray-workflows-cloud-edge-vX.Y.Z.zip`. If a harness change alters the ZIP output, bump `harnessRef` first (variants + includes need harness ≥ v2.2.0).

## Two editions, one code base

| | `onprem` (default variant) | `edge` variant → `cloud-edge` bundle |
|---|---|---|
| Transport | Groovy `HttpURLConnection` (`shared/dxr_http_direct.groovy`) | Collibra **External API task** bound to an Edge HTTP connection (`shared/dxr_edge.groovy`); scripts never open HTTP |
| DataXray endpoint | `GET /api/v1/files?q=<KQL>` NDJSON stream (whole result set), `GET /api/v1/classifications` | `POST /api/indexed-files/search` (internal, paged, JSON `query_items`) + 4 small internal catalogue endpoints; `GET /api/v1/classifications` |
| Config variables | `dataxrayUrl`, `dataxrayAuthToken` (sentinel defaults) | `dataxrayConnectionName` (default `data-xray`), `dataxrayPageSize` (25, max 100; search preview, import, rerun), `dataxrayUrl` (links only, optional). **Switching editions loses the variables the other edition does not declare** (Collibra drops undeclared formProperty values) — re-enter the Bearer token when going back to on-prem. |
| Fetch shape | one sync script streams everything into a gzip+Base64 work list; async batch task ×50 | loop: script arms request → External API task → script handles page; **page = batch**, no work list |
| Search results | preview + full CSV ZIP attachment | preview + the same ZIP'd CSV (Datasource,Path), collected in a second pass after the preview: `beginEdgeFilesPass(edgeResultsFileExcludedFields())`, 100 slim rows per request on the preview's PIT, chunks in `resultsFileChunk_<n>`, zipped by `search_finalize_edge.groovy`. None above `dxrEdgeResultsFileMaxRows()` (10,000) / `max_result_window`; a failure only changes `attachmentDescription`. Every pass (preview, file, import, rerun) starts with `beginEdgeFilesPass()`, which resets the shrink/skip state and the field exclusions |
| Failures after the first task | `WorkflowException` rolls back into the start dialog | cannot (async): `searchFailed`/`syncFailed` → *Search Failed* / *Sync Failed* user task; rerun sets `rerunAborted` (form shows the reason) |

Everything Collibra-side (asset upsert, relation reconciliation, formerly-swaps and Not in any search, classification sync, criteria rebuild) is shared: `shared/file_batch.groovy`, `classification_sync.groovy`, `rerun_common.groovy`, `search_common.groovy`, `collibra_lookup.groovy`. `configure-data-xray-workflows` and `sync-data-xray-files-nightly` are identical in both editions. Shared files hold only `def` functions and use fully-qualified DTO names (imports must stay at the top of the glue script). The harness includes each file once per script, so diamond includes are fine.

## Edge edition internals (verified on ohalo.collibra.com, Collibra Cloud 2026.09 + Edge 2026.6, Sept 2026)

**External API task** (`<serviceTask flowable:type="http">` + `<design:http-connection-name>${dataxrayConnectionName}</…>`): method/path/headers/body are expressions (`dxrMethod`, `dxrRequestPath`, `dxrRequestHeaders`, `dxrRequestBody`, armed by `armEdgeRequest`); the relative path is appended to the connection's Host; response body → `dxrResponseBody` (String), `dxrResponseStatusCode` (Integer), `dxrResponseReason`, `dxrResponseHeaders`. Every status is "success" (a 404 is just status 404). Response cap: **100 KB** (confirmed by Collibra support for TRC's instance, Sept 2026; ohalo.collibra.com happened to allow ~512 KB — do not rely on that). An oversized body sets `dxrErrorMessage` = *Response size exceeds the allowed limit.* and, with `ignoreException=true`, the flow **continues** with no body — `readEdgeResponse()` turns that into a retry/abort/fallback. ~0.5–2 s per call. **A non-existent connection name is a pre-validation failure: the instance goes into error (dead-letter job), no task, nothing a script can catch** — documented in the Edge guide's troubleshooting table. `execution.removeVariable` works; `readEdgeResponse()` clears the response variables so a retry can never read a stale body.

**Why the internal search API**: `/api/v1/files?q=` exports the whole index and filters the KQL in memory (`FilesV1Resource` + `KqlResponseFilter`), so it cannot be paged. `POST /api/indexed-files/search` pages with `pageNumber/pageSize`, keeps a consistent snapshot with `usePIT`/`pitId`, returns an exact `hits.total.value` and `max_result_window` (10,000 default; 30,000 on demo), and accepts `excludedFields` with wildcards. Sort `[datasource_id asc, ds#file_name.raw asc]` (what DXR's own export uses) makes from/size paging stable. Ceiling: a query with more hits than `max_result_window` can be previewed but not imported (refused with a message).

**Row → tuple mapping** (`tupleFromSearchHit`): `_id` → fileId; `ds#file_name`, first `ds#parent_folder_paths` + `/` + name → path; `ds#file_size`; `metadata#MODIFIED_DATE`; `datasource_id` → name via `/api/datasources/browse`. Classification refs: labels = `dxr#tags` (numeric tag ids → uuid via `/api/tags`), annotators = `annotation_stats#unique_phrase_count.<numericId>` > 0 (→ uuid via `/api/data-classes`, six lists incl. read-only ones), extractors = `extracted_metadata#<numericId>` non-empty (→ uuid via `/api/metadata-extractors`). Those UUIDs are what `/api/v1/classifications` returns and what Collibra stores in the DataXray ID attribute, so the existing byDxrId/byName index resolves them. Search and rerun make **no catalogue calls**: the Edge-edition classification sync stamps each asset's numeric index id in the **DataXray Index ID** attribute (`dataxrayIndexIdAttrTypeId`, created by configure), and `buildEdgeClassificationIndex()` derives every mapping from Collibra. Datasource names are fetched per id (`GET /api/datasources/<id>`, header `api-version: V3`) the first time a page mentions the id and cached in `dxrDatasourceNames`. **Classification sync (`shared/dxr_edge_sync.groovy`)**: `/api/v1/classifications` is one body (~340 B/item, ~300 KB at TRC) so it is never used through Edge; the sync loads `/api/tags`, `/api/metadata-extractors` and the complete `/api/data-classes`, and when Collibra refuses the last one as oversized it falls back to `/api/datasources/ingester/index/classes` (annotators **with findings** only — NOT the catalogue; trusting it as complete retired 45 dev assets on 2026-09-16) plus `/api/data-classes/<id>` per unknown annotator, and in that mode never retires annotators (`noRetireTypeIds`). The sync must run before the first Edge search (`edgeUnresolvedMessage`).

**Criteria → `query_items`** (`composeEdgeQueryItems`; each criterion its own AND group, `group_id` increments): label `{parameter:"dxr#tags", value:"<tagId>", type:"number", match_strategy:"exact"}`; annotator `{parameter:"annotators", value:"annotation.<id>", type:"text", match_strategy:"exists"}`; extractor `{parameter:"extracted_metadata#<id>", type:"text", match_strategy:"isSet"}` (`exists` → HTTP 400); phrase `{parameter:"annotation.<id>", value:"<text>", type:"text", match_strategy:"contains"}` repeated per picked annotator inside one group (first `AND`, rest `OR`; no annotators picked ⇒ every annotator in the catalogue). A criterion whose UUID the catalogue lacks → unresolved → clean failure, never a broadened query. **Gotcha:** the catalogue is what the *connection's* DataXray user can see — a label synced by a user in another organisational unit is "not visible through this connection".

**Page sizing**: `edgeExcludedFields()` drops phrases, raw text, computed/entitlement fields → 25 rows ≈ 30–40 KB under the 100 KB cap. `dataxrayPageSize` defaults to 25 (BPMN default too — it was 50 until Sept 2026) and is clamped to 1–100 (`dxrEdgeDefaultPageSize`/`dxrEdgeMaxPageSize`); the search preview, import and rerun all use it. Rows are much larger on some instances (TRC, Sept 2026: 50 rows > 100 KB), so an oversized page is **not** retried as-is: `shrinkEdgeFilesPage` re-arms the same rows with the largest size ≤ half that divides the row offset (DXR pages from `pageNumber × pageSize`), keeps it for the rest of the run (`dxrPageSizeCur`; offset is always `dxrPageNo × dxrPageSizeCur`), and once one row alone is too large, re-asks for that row with `excludedFields: ["*"]` (DXR passes it to ES `_source.exclude`: ~400 bytes, `_id` only — verified on demo 2026-09-28), skips it (`skipEdgeRow`, `opts.onSkip`: counted as failed; the rerun adds it to the seen set, or sets `rerunRetireUnsafe` if the id could not be read) and grows back towards the largest size that worked (`dxrPageSizeOk`, `dxrRegrowTo`). `onPageZero` runs on the first page that *arrives* (`dxrFirstPageDone`), which is not page 0 when row 0 was skipped. The import starts at the size the preview ended on. Rerun chunks (`rerunSeenChunk_<n>`) count processed pages, not `dxrPageNo`, which is renumbered on a shrink. **Refusals arrive in two forms** (`isEdgeRefusal`): the explicit *Response size exceeds the allowed limit.* error, or an HTTP **5xx with an empty body** while DataXray's nginx logged 200 (TRC, 2026-10-09: three 190 KB pages). A real DataXray error always carries a JSON body, so it is retried, never shrunk. If even the one-row `_id` lookup fails, the run aborts (DataXray/Edge down) instead of skipping every row.

**Testing recipe**: deploy with `--variant edge`; on ohalo.collibra.com the Edge site `ohalo-edge-integration` has two HTTP connections: **`data-xray`** (Basic auth, a dedicated DXR service account in the same organisational unit as the on-prem Bearer token's user — use this one; credentials live only in the harness `.env`) and the older **`ohalo`** (user `life_sciences` @ demo.dataxray.io — org unit 8, so its labels differ; read-only annotators such as *Email (Regex)* are visible to both). Start workflows via `POST /rest/2.0/workflowInstances` passing `formProperties.dataxrayConnectionName` = `data-xray` (for the rerun: `businessItemIds: [<query asset id>]`, `businessItemType: "ASSET"`); poll `GET /rest/2.0/workflowTasks` for the instance's task (async: the results task appears ~7 s later); `GET /rest/2.0/workflowTasks/{id}/taskFormData` exists but exposes no variables for HTML forms, so verify via the query asset (attributes, relations) and the Files domain. Verified 2026-09-15: search 64 hits → import 64 file assets in 2 pages (~7 s) with correct attributes and classification links; rerun kept 64 `returns` relations; wrong connection name → instance in error. Verified 2026-09-16/17 with the numeric-id design through `data-xray`: Edge sync stamps 69/77 index ids (the 8 unstamped are one Obsolete label and 7 legacy `ANNOTATOR_DOMAIN` assets neither edition manages), retires nothing; search 200 hits → import 200 files in 8 pages of 25; interactive rerun 12 s keeping 200 relations; the 02:00 nightly Edge sync left the domain unchanged. Don't run the classification sync through `ohalo` on dev: it would retire every classification of the other org unit.

**Version stamp** (v2.3.0, harness ≥ v2.4.0): `dxrPackVersion()` / `dxrPackEdition()` in `dxr_model.groovy` hold `{{pack:version}}` / `{{pack:variant}}`, filled in at build time (release tag, or `dev-<commit>[-dirty]` for a dev deploy). Every entry script calls `announceDxrVersion('<workflow>')` first (logs it, sets `dxrVersionLabel` for the `dxrVersionFooter` row of every result/summary/failure form); `edgeRetry`'s final error line carries it; every `app.json` description ends with *DataXray workflows {{pack:version}} ({{pack:variant}}).*, so the overview page and `GET /workflowDefinitions/{id}` show it.

## DataXray rename (Oct 2026)

The product was renamed from *Data X-Ray* to *DataXray*, and the queries domain from *Data X-Ray Custom Queries* to *DataXray Sync Filter*; v2.7 renames the query asset type *Unstructured Data Query* to *DataXray Sync Filter* too (agreed with Colin, 23 Oct: a saved search is really a sync filter; an asset-type def's `legacyName` overrides `legacyName()`). Code, variables and docs still say "query" for it. Only names people see changed: process ids (`searchDataXray`, …), directory and script names, variables, tags (`dataxray-*`), the bundle name (`collibra-data-xray-workflows-…`) and the default Edge connection name (`data-xray`) are unchanged, and LICENSE keeps its trademark wording. Configure's Phase 6b (`renameIfLegacy`) renames existing elements, and Phase 7 the workflow definitions (a redeploy keeps a definition's old name), but only while an element still has its old default name (`legacyName()`), so customer renames survive. Verified on ohalo.collibra.com, 23 Oct 2026.

## Access control for the DataXray workflows

Two custom **global roles** gate the DataXray workflows. Both are created (idempotently, with fixed canonical UUIDs) by `configure-data-xray-workflows`:

| Role | UUID | Purpose |
|---|---|---|
| `DataXray Admin` | `019e9000-abcd-7000-a115-74a17d050000` | Granted the `WORKFLOW_ADMINISTRATION` global permission so holders (alongside Sysadmins) can edit each workflow's Base URL + Bearer token. ⚠️ That permission is **global** — it confers admin over *all* workflows on the instance; Collibra has no per-workflow admin permission. |
| `DataXray User` | `019e9000-abce-7000-9e7d-a7a7115e0000` | Bare membership role, no permissions. Only gates who may *run* the search/sync workflows. |

**No delete-enforcement role**: a "Classification Manager" resource role (mirroring Admin membership onto the Classifications domain via responsibilities) was built, verified and then **deliberately rolled back** (Aug 2026) — Collibra's default already denies asset deletion to anyone without an explicitly granted delete-capable responsibility, so the extra role added moving parts without adding real protection. The guidance is documentation-level: don't grant Steward/Owner-style responsibilities on the Classifications/Files domains. (Learned along the way, kept for reference: `responsibilityApi` IS injected into workflow scripts even though `stubs/CollibraStubs.groovy` doesn't list it; resource permissions on a *global* role would apply instance-wide, so scoped grants require a resource role + responsibility.)

**Who can run** = the workflow definition's start roles, set *only* at runtime by `configure-data-xray-workflows` (Phase 7) via `workflowDefinitionApi.changeWorkflowDefinition(...)` with `startRoleIds`. This is a **partial PATCH** — only `startRoleIds` is sent, so configuration variables (the admin-set token/URL) are **not** wiped. search/sync/rerun → User + Admin; the two nightlies + configure → Admin.

⚠️ **The BPMN's `flowable:candidateStarterGroups` is inert in Collibra** — verified by test: a fresh deploy lands with *no* start-role restriction (`startRoles` empty) regardless of what the attribute says, and configure's BPMN says `flowableUser` yet its enforced `startRoles` is `[DataXray Admin]`. Leave it at the canonical `flowableUser` (matches real Workflow Designer exports); do **not** try to encode access there. The read model exposes start roles as `startRoles` (array of role objects); the *request* field is `startRoleIds` (UUIDs) — don't confuse the two when inspecting via REST.

**Start roles persist exactly like configuration variables.** An in-place redeploy/re-import (POST upsert, same definition UUID) **preserves** `startRoles` — verified. They reset to unrestricted only if a workflow is **deleted** and reimported (same rule as config vars). So after a delete+reimport, **re-run configure** to re-assert access.

**Configuration variables are not per-role.** `readable="false"` already hides the Base URL + token from *everyone* who starts a workflow (any role); only Sysadmin / `WORKFLOW_ADMINISTRATION` holders can edit them on the settings page. Granting `DataXray Admin` that permission is the only lever — nothing "hides" the token from Users because it already is hidden.

**Bootstrap (2 steps).** Import/deploy all six workflows, then run `configure-data-xray-workflows` once (as a Collibra admin / Sysadmin) — it creates the roles and stamps `startRoles` on every deployed target in a single pass. configure skips run-access for any workflow not yet deployed, so if you run it before everything is imported, **re-run it** once the rest are in.

## File import model (gated import + rerun + nightly sync)

Search results can be imported as **DataXray File** assets in the **DataXray Files** domain (canonical UUIDs in `configure_data_xray.groovy`, mirrored in `dxrModelIds()` in `shared/dxr_model.groovy`). v2.4 added three, all created by configure: status **Not in any search** `019e9212-0a11-7c3e-9b2f-5d4e6f7a8b90` (added to the File assignment), relation type **formerly returns / formerly returned by** `019e9212-1b22-7d4f-8c3a-6e5f7a8b9c01` (query → file) and **formerly groups / formerly grouped by** `019e9212-2c33-7e50-9d4b-7f6a8b9c0d12` (file → Data Asset, so it reaches Label/Annotator/Extractor). Key mechanics:

- **Upsert key**: a new asset's UUID = `UUID.nameUUIDFromBytes("dxr-file:" + dxrFileId)`, and `assetApi.exists(id)` is the first check. **Object key (requirement #1, v2.6, Cloud + Edge)**: tuple [8]/[9] = the hit's `datasource_id` / `object_id`, stored as *DataXray Datasource ID* / *DataXray Object ID*; a tuple whose file-id UUID has no asset is looked up in `loadFileObjectKeyIndex` (`"<dsId>:<objectId>"` → asset, built once per run from two attribute scans, cached gzip+Base64 in `dxrObjectKeyIndex`) — this keeps assets through an index drop + rescan (same datasource id and object id, new file id). `processFileBatch` returns `seenAssetIds` (resolved), which the Edge rerun's `afterPage` records for the retire pass; `onSkip` marks the retire pass unsafe when the skipped file's id-derived asset doesn't exist. On-prem `/api/v1/files` rows carry no object id (checked Oct 2026; its `datasource.id` is a UUID, the index's is numeric), so on-prem tuples leave [8]/[9] empty and on-prem identity is the file id only. `rerunModelGap` requires both attribute types (run Configure).
- **Names**: full name = filename + ` [8-hex-of-UUID]` suffix (per-domain name uniqueness vs duplicate filenames at 10k scale); clean filename in `displayName` (the File type has `displayNameEnabled`). **Both set only at creation (v2.7, TRC story #24)**: a rename in Collibra sticks; DataXray's current filename is written on every sync to **DataXray File Name** `019e9212-5f66-7183-a07e-ac1d2e3f4a45` (in `rerunModelGap`). Every other file attribute is still overwritten from DataXray.
- **Per-query membership**: dedicated **returns/returned by** relation type (query → file). Do NOT use `groups` (7017) for this — 7017 already means query→classification and file→classification.
- **Park, never delete** (`retireOrphanFiles` / `parkFileAsset` in `file_batch.groovy`): a rerun swaps the query's `returns` link to each file it no longer returns into `formerly returns`, and sets **Not in any search** only on files **no** `returns` link is left on (`formerly` links never count); `processFileBatch` sets Candidate `…005008` and swaps the link back on reappearance. Obsolete `…005011` now means only "deleted in DXR" (classifications; the classification sync is unchanged); for files it is legacy — treated like Not in any search (`isParkedFileStatus`). A run that returns **0 results**, or is aborted/partial, skips the pass (transient-outage guard).
- **Person-set statuses are never changed**: the integration owns only Candidate / Not in any search / Obsolete on file assets (`isIntegrationOwnedFileStatus`); any other status (Accepted, Under Review, …) is kept by rerun and sweep, while attributes, relations and link swaps still happen. Agreed rule: a file asset a user has marked active is never made obsolete by DataXray.
- **Rerun model guard**: `rerunModelGap()` makes both rerun collectors abort ("run Configure first") while the status or either formerly relation type is missing; the nightly sweep is skipped (logged) without the status. Hence the upgrade step: re-import, then re-run configure.
- **Batch loop**: on-prem, the collector script (sync) streams the DXR NDJSON into a gzip+Base64 JSON work-list process variable and an **async** script task processes 50 items per execution/transaction, looped by an exclusive gateway on `${hasMoreWork}` — Collibra's prescribed bulk-ops shape; the blob is written once, only an integer cursor advances. In the Edge edition there is no work list: each External API task fetches one page and the following script upserts it as one batch (`handleEdgeFilesPage`). Both call the same `processFileBatch` (`shared/file_batch.groovy`).
- **Instance-wide cap**: max **25,000** DataXray File assets **by asset type** (`countFileAssets`, so moved assets count; projected = current population + net-new), warning above 5,000 (`dxrWarnImportFiles`). **Per-run limit** `dxrMaxImportFiles()` = 10,000 (TRC, 13 Oct): a search above it can't be imported or kept in sync (`syncOffered` false), both import collectors re-check it, and a rerun creating more than 10,000 new assets is refused (on-prem exact `newFiles`, Edge `growth` estimate in `onPageZero`). Enforced in the scripts (forms are bypassable), surfaced via form visibility bindings. Import/rerun refusals say "Collibra holds N DataXray file asset(s)"; the results-task message (`search_common.groovy`) still says "the DataXray Files domain holds". A `dataxray-no-auto-import` rerun projects 0 new.
- **Search results task options** (independent): Import now (`importDecision`), Keep in sync nightly (`keepInSync`), Create assets for new files on later reruns (`autoImportNewFiles`, default true); the two sync options show when `syncOffered` (0 < total ≤ 10,000). `queryFlagsTask` (`apply_query_flags.groovy`, synchronous, both BPMNs) runs right after the results task, before the import gateway, and writes the tags — the import collectors no longer tag.
- **No auto-import**: tag `dataxray-no-auto-import` on the query → the rerun sets `rerunNoAutoImport`, `processFileBatch(..., [createNew: false])` refreshes/links existing assets only and counts the rest as `skippedNew` (`importSkippedNewCount`, *Not imported* on the summary form).
- **Keep-in-sync**: tag `dataxray-keep-in-sync` on the query asset; `sync-data-xray-files-nightly` (02:30, after the 02:00 classification sync) starts one **headless** `rerunDataXraySearch` per flagged query via `startWorkflowInstances(... formProperties([headless: 'true']))`. Headless runs never throw and skip the summary user task via a gateway on `${headless == 'true'}`. Flagged queries whose status is **Obsolete are skipped** — archiving a query pauses its nightly sync (manual rerun still allowed); reactivating resumes it. The driver then runs an **orphan sweep**: every DataXray File asset **by asset type** (`eachFileAsset`, so moved assets are included) with no "returns" relation from any query goes through `parkFileAsset` → Not in any search — this is what cleans up after a *deleted* query asset (Collibra deletes its relations with it, and per-query passes can never see it). It also migrates pre-v2.4 Obsolete orphans on its first run. **Existence check (v2.7, Edge only, TRC story #31)**: `workflow.edge.bpmn.template` of the files nightly adds prepare (`exists_prepare_edge.groovy`) → External API task → `exists_page_edge.groovy` loop after the driver, with its own `dataxrayConnectionName`. Every asset with status Not in any search / **Not in DataXray** (`019e9212-6a77-7294-b18f-bd2e3f4a5b56`, created by configure, in the File assignment) and an object key is looked up per datasource, `dxrExistsCheckBatchSize()` = 200 object ids per request: `(datasource_id = D) AND (object_id = o1 OR …)` with only those two fields returned (~250 B/hit; verified on demo 23 Oct: 1,000 ids in ~1 s; a datasource id DXR doesn't have returns 0 hits, not an error). Not found → Not in DataXray; a Not in DataXray asset found → Not in any search. No rescan guard: DXR updates the index in place during scans. The search API cannot look files up by `_id`/file id (all tried field names return 0) and there is no single-file endpoint, so assets without an object key (orphaned before v2.6) are skipped and counted (`nightlyExistsNoKey`). `parkFileAsset` keeps Not in DataXray; `isParkedFileStatus` / `isIntegrationOwnedFileStatus` include it. Logic in `shared/file_exists_edge.groovy`. The sweep aborts on any scan failure rather than acting on a partial picture. Timer-start workflows can also be started manually via `POST /workflowInstances` (verified) — handy for testing.
- **Relation reconciliation**: the batch stage diffs each pre-existing file's `groups` links against the row's current hit evidence — a stale link (label deleted/unassigned in DXR) is swapped to `formerly groups`, and swapped back when the evidence returns. A result row carries the file's complete classification state, so this is query-independent. **createdBy rule**: only links whose `createdBy` is the integration (`integrationIdentityIds()`: Collibra's Workflow user `00000000-0000-0000-0000-000000900003`, which async tasks run as — nothing else) are removed or swapped; a person's link is never touched, and its presence means no duplicate is added. Caveat: the customer's own workflows also create links as the Workflow user, so they are indistinguishable from ours.
- **Rerun exclusivity/scoping**: `rerunDataXraySearch` runs with exclusivity `UNCONSTRAINED` (default RESOURCE_EXCLUSIVITY hides the start action while a summary task is open and would block the nightly fan-out). It cannot be scoped to the query asset type — asset-type assignment rules reject workflows with **global** start roles (`workflowWrongRoles`) — so `rerun_collector.groovy` hard-guards the item's asset type at runtime.
- **Rerun criteria**: rebuilt from the query asset's 7017 relations (classifications' **current** names — DXR renames just work) + the "Annotated Text Filter" attribute, scoped to the annotators linked by the query's **searches text in / text searched by** relations (`019e9210-f2a1-…`, created by configure). Composition: every label/extractor/annotator is its own AND clause; the phrase clause is `annotators: { (name:"A" OR name:"C") AND annotations.phrase:"*text*" }` — OR only between the annotators explicitly picked for the text (agreed with Colin Walker, Aug 2026). A criterion whose asset is Obsolete (deleted in DXR) fails the rerun with a message naming it — never silently broadens the query. The "DataXray Query" attribute is a human-readable record of the last run, not rerun input.
- **Verified 22 Oct 2026** on ohalo.collibra.com, on-prem edition: Configure creation + idempotency, formerly swaps both ways, person-set status kept, person-made link kept/no duplicate, two-query file keeps status, no-auto-import rerun, keep-in-sync without import, Obsolete → Not in any search migration. Same scenarios then re-run on the Edge edition (connection `data-xray`) once the dev Edge site was fixed: all pass. Note for debugging Edge: "Edge request failed: IO exception occurred" with no status/body is the Edge site failing to reach DataXray (released v2.3.0 failed identically), not the workflow; the Edge site's health status in Collibra does not cover it.
- **DXR row-shape assumptions** live in exactly two shared functions: `extractFileTuple` (`shared/dxr_rows.groovy`, `/api/v1/files` rows — on-prem) and `tupleFromSearchHit` (`shared/dxr_edge.groovy`, internal search hits — Edge). Both produce the same work-item tuple. Verify against a live response when DXR versions change. Hit-evidence rule: a classification listed as *checked with 0 hits* must NOT get a relation (on-prem: `uniquePhrases`/`annotations`; Edge: `annotation_stats#unique_phrase_count.<id>` > 0).


## DataXray API facts (verified against a DataXray demo instance, 2026-08)

- `/api/v1/files` NDJSON row: `fileId` (not `id`), `fileName`, `path`, `size`, `lastModifiedAt`, `datasource: {id, name}`, `labels: [{id, name}]`, `extractedMetadata: [{id, name, value, type}]`, `annotators: [{id, name, uniquePhrases, annotations: [...]}]`. **No UI link field** on file rows — don't fabricate deep links.
- Extractor results are queried via **`extractedMetadata.name:"X"`** — `extractors.name:"X"` matches nothing.
- File rows list annotators only with hit evidence fields (`uniquePhrases`/`annotations`); labels/extractedMetadata by presence.
